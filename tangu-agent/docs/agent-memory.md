# Agent 隔离记忆与 Dream 整理

2026-09-08 实现。参考 Hermes 的小常驻记忆与按需历史检索、Hanako 的来源覆盖与提交前验证、OpenClaw 的遗忘标记；按 Tangu 现有多 Agent 架构重新接入，没有引入它们的全局记忆池。

## 使用

- 对话里的 `remember` 支持 `add`（默认）、`list`、`update`、`forget`。更新/遗忘先取得条目 ID；工具回执只含实际持久化后的版本与**受影响的那一条**（不再整份 entries 回灌上下文；重复写入回 `duplicate: true`）。Chat 模式也可用。失败不能宣称“已记住”。
- 模型调用必须显式提供 `action` 和 `fact`：`add/update` 的 `fact` 是非空、最多 300 字符的持久事实，`list/forget` 用 `fact: null`。更新须同时带 `id` 和 `expectedVersion`。漏传或类型错误时不写入，回执给出带原 ID/版本的纠正示例；执行入口仍兼容历史 `add` 默认动作及不带 `fact` 的读取/遗忘调用。
- 前台主循环中，若整轮工具均失败，且调用参数与错误连续三轮相同，下一轮关闭工具并说明相关操作未完成。比较忽略 JSON 空白、对象键顺序和工具调用 ID；纠正参数、改变错误、任一成功结果或用户追加指令都会重置计数，不影响正常多步任务。
- **形状闸（2026-09-22，借 Hermes memory 工具）**：单条 `fact` 超过 300 字直接拒绝并指向 `log_event`（与 Historian 候选采集的 300 字截断同口径）；描述与运行时指引明说「记忆 = 下个月仍成立的事；进度 / 交付物 / 版本号 / 带日期的进度汇报归日志」（生日、财年截止这类带日期的稳定事实照记），新事实取代旧条目时 `list` → `update` 原地替换而不是再加一条「更正」；记忆满（20,000 字）时回执列出现有条目与版本，让模型一次删旧加新。**为什么**：一份终端用户导出里 41 条显式条目最长 1,477 字、21 条带日期、9 条是追加式更正——显式路径此前没有任何闸，而候选路径 12 天只出 8 条一句话；措辞已经写在该 Agent 的 developer_instructions 里却挡不住，只有执行层挡得住。辅助模式讨论同步注入整份记忆（受同一 20k 帽）而非头 3,000 字，否则主 Agent 看不到最新条目。
- 设置 → 智能体 → 某个 Agent 的记忆：查看/编辑/遗忘条目、检查来源、编辑原文、查看版本与恢复。原文和日志编辑必须提交读取时的版本；409 保留草稿，先刷新后合并。
- Dream 在同一面板中操作。可单次“立即整理”，也可单独关闭此 Agent 的自动整理，设置模型、最小间隔、总时限与输出预算。模型留空沿用已配置的后台模型（与 Historian 同一条解析链）。
- **自动整理自 2026-09-19 起默认开启**（此前默认关闭）。原因：Historian 只写候选，Dream 是候选进入 MEMORY.md 的唯一通道；默认关闭时，原装安装会一直采集候选却永远记不住。配套三条：①`.memory-dream.json` 带版本标记 `v: 2`——没有标记的旧文件里的 `enabled: false` 是旧默认值随状态写入顺带落盘的，不是用户的选择，读作开启；带标记后的 `false` 才是用户关掉的，永久保留。②自动运行在“没有已核验的新候选、且记忆版本就是上次整理产出的那一版”时直接跳过，不调用模型；手动整理不受此限。③没有可用后台模型时自动运行记为跳过而非失败。
- 辅助模式（`historian.mode = 'assist'`）的到点轮同样检查整固：辅助模式只表示本轮不由 Historian 采集候选，收件箱里已有的候选仍只有 Dream 一条路进入记忆。
- Historian 仍单独控制从对话采集候选。关闭 Historian 时，Dream 可以整理已显式保存的记忆，不会擅自扫描所有对话来创建候选。

## 隔离契约

记忆条目、版本、墓碑、候选和 Dream 状态属于 `agents/<memorySlug>/`。模型工具没有可自行指定的 `agentSlug` 参数；其身份来自可信运行上下文。历史搜索与读取另外按 `(userId, appId, activeAgentSlug)` 检查归属，猜中另一个 Agent 的 session/message ID 也不能读取。无 Agent 标记的旧会话只归默认 Agent。

保留用户已有的 `shareDefaultMemory=true` 例外：该 Agent 明确共用默认记忆域；展示身份、会话归属仍是原 Agent。后台同步使用展示身份选文件，不能把 memorySlug 当成同步目标。新开云同步默认不授权旧全局 USER/MEMORY 池；共享必须另有显式配置。管理者界面仍可以查看自己的各 Agent。

这是应用层作用域，不是多个 OS 用户。Tangu 本地数据库和 home 仍是每安装单用户。是否约束任意主机命令，取决于另行配置的 OS 沙箱；参见 [runtime-safety.md](runtime-safety.md)。记忆/日志/历史工具是固定参数的可信应用状态入口，不接受任意磁盘路径。计划模式原有写入限制继续适用。

## 存储、遗忘与恢复

- `.memory-state.json` 是事务真源：活跃条目、UUID 版本、来源/证据 ID、最多 100 条历史修订、遗忘/重新记住事件、最近 8192 个已处理候选 ID。`MEMORY.md` 是兼容人工编辑的投影。
- 同目录短事务互斥；临时文件、fsync、原子 rename；`projectionPending` 能恢复“元数据提交后、Markdown 投影尚未完成”的中断。网络和模型调用不持有目录锁。
- 文件不存在与 EIO/EACCES、损坏 JSON、未知结构明确区分。损坏/读失败不会伪装为空白覆盖旧数据。已有 state 时直接删掉 MEMORY.md 是损坏，不是遗忘。
- `forget` 删除活跃记忆并留下防重放事件；自动检索排除已知遗忘原文/证据，Dream 与同步不能用已知旧来源恢复它。版本恢复也不自动复活遗忘条目。只有显式 add/update 可以有意重新记住。
- 跨设备合并分别保留最新的 forget 与 restore 时间；观察到遗忘后的显式重新记住优先，无法判定先后的同时间冲突以遗忘优先。
- **遗忘不是物理擦除**：版本历史和墓碑仍含原文供审计；对话原文也不会因此被删除。对未知来源的语义改写，不能保证靠指纹自动识别。不要将此功能描述成账户数据彻底删除。

若进程在持锁时崩溃，遗留 `.memory.lock` 会明确返回 `MEMORY_BUSY`，不会按年龄抢走可能仍在使用的锁。恢复步骤：停止此 home 的全部 Tangu 引擎/Desktop/TUI，核对锁内 PID 已退出，备份该目录的锁、state 与 MEMORY.md，将锁移到备份位置后重启。读取会按 pending 标记恢复投影。不要在其他写者仍运行时盲删锁；无法确认归属时保留现场。

## Dream 提交流程与预算

1. 读取此 Agent 的版本快照，并根据事务中的候选回执补做上次未完成的收件箱清理。
2. 轮转读取最多 12 个候选（无证据旧条目不会阻挡后续候选），校验来源会话归属，按采集时的消息锚点读取有界证据。不能核验的候选留待审阅，不交给模型自行丢弃。
3. 一次模型调用提出按 source ID 分组的事实与候选丢弃理由。代码要求所有既有事实被覆盖恰好一次，未知 ID、重复覆盖、遗漏、删除已有事实、超过 20,000 字符或截断输出均拒绝。**`keep`（2026-09-22）**：未变的既有事实只回 ID，校验器按存储顺序展开成原文后再提交——输出随改动量而不是记忆总量增长（此前要逐字重发全部事实，17k 字的记忆估 ~7.7k tokens，默认 3,072 输出预算永远塞不下）。给模型看的 source ID 是短别名 `m1…`/`c1…`（UUID 一个 ~25 token，几百个 keep 本身就能撑爆输出预算），提交前映射回真 ID；核验调用拿的是紧凑形（keep 的 ID + 改动组），不把 keep 展开成原文再灌一遍。
   - **输入预算按余量裁证据（同日）**：32,000 字符预算 = 既有记忆 JSON + 候选证据；候选逐条按余量裁证据尾窗（锚点消息在末尾，留尾），低于 1,000 字符的**跳过继续**（后面窗口更短的候选照样能塞下），跳过的和来源查询抛错的都留在收件箱、游标照常越过（转到队尾，不会每轮堵在最前让 Dream 永远失败），状态里写明 `N deferred by the input budget`。此前 12 条 × 8k 证据不看余量，记忆稍大整轮即 `failed, calls: 0`，每 6 小时原样重演、收件箱永不排空。既有记忆单独超预算仍是明确失败（只可能来自面板 / 同步写入的超帽内容）。
4. 第二次调用核验事实、条件、路径、日期及例外没有丢失，候选有对话证据支持。不会为了通过验证反复追加修复调用。
5. 用读取时的版本 CAS 提交正文、来源和候选处理回执。并发修改则拒绝，原记忆和候选保留。提交后清理失败可下次恢复；已经提交就报告已完成，不能误报成取消。

默认每 Agent 间隔 6 小时、总时限 60 秒、两次调用合计最多 4096 输出 tokens（提议 75%，验证 25%），进程同时最多 2 个 Dream；不排无限队列。自动触发依附用户 run 完成，不是独立定时守护。Historian 自己最多 2 个同时运行、单次总时限 90 秒。

Provider 的 build/stream 接收真实 AbortSignal；每次持久化前再次检查取消。若第三方适配器忽略信号，状态会说明正在等待停止，保持单飞且拒绝迟到结果；不能把超时当成实际请求已经结束。模型和同步已经在远端提交的副作用不能靠客户端取消撤回。

## 前台性能与历史召回

每个 run 冻结最多 **4000 字符**记忆上下文：约 1000 常驻、2000 相关条目、1000 相关历史证据，包含来源标签的总量也受硬帽限制。采用本地词法相关性，支持中文分词；没有嵌入请求，也没有全库建索引阻塞启动。

自动历史窗口最多 16 会话 × 每会话最近 16 条 × 每条前 2000 字符；显式 `search_sessions` 最多 64 × 64 × 4000。搜索结果提供原始 message ID，`read_session` 支持精确回读/翻页；找不到时应提示窗口限制并用日期缩小范围，不能声称已穷尽全部历史。没有持久派生索引，所以会话 purge 后不会从旧索引复活。

Agent 定义已有有效本地快照时立即开跑，云文件同步在后台进行；只有首次水合等待云端，带 15 秒总 deadline/取消。缺失或失败不会偷偷换成默认 Agent 继续。同步逐请求、逐本地提交复核账号来源、授权修订和取消状态；LOG 在网络返回后重读并 CAS，部分失败明确返回失败。

云端只接受固定文件名单、合法 slug、真实日期和无穿越的路径，拒绝逐段 symlink；记忆 tombstone wire 为 `.memory-tombstones.json`，配置、候选、事务 state 与本机运行状态不镜像。旧云端不支持必要的 seq/hash/CAS 时，危险覆盖会明确拒绝，需升级服务端，不能退回悄悄覆盖的 LWW。

## 召回块的落点(2026-09-14 起)

`buildAgentMemoryContext` 返回的三段现在分开出账:`stable` = §1 存储证据(与本条消息、本会话都无关,Dream 之间稳定),`volatile` = §2 按查询打分 + §3 跨会话历史片段(带 `[session_id=…; message_id=…]`,每条消息都不同)。`content` 仍是整块,恒等于 `[stable, volatile].filter(Boolean).join('\n')`。

落点由 `TANGU_MEMORY_VOLATILE` 决定:

| 取值 | 易变段去哪 | 用途 |
|---|---|---|
| `tail`(缺省) | 对话尾部 user 消息(与 `/skill`、`@` 提及、运行时 git/todo 同一条通道),不落库不上屏 | 让系统提示前缀跨会话可共享 |
| `system-end` | 仍在系统消息里,但挪到 `systemParts` 最末尾 | 变体 S:不改「记忆是 system 角色」的权重 |
| `system` | 旧位置(记忆块整块留在系统提示 44% 处) | A/B 基线,与改动前逐字节一致 |

稳定段恒留原位。`sketchTurnSignal`(按本条消息的正则取 3 种值)跟易变段同一落点。

**为什么**:易变段卡在系统提示中部,等于每来一条新消息就把它后面的技能目录与 ~13k 工具头一起从缓存里作废;实测同 agent+模型的不同会话,系统提示正是在记忆块处首次分叉。

**代价**:`tail` 档下,开发者「显示 system prompt」事件与 context 视图的 `memory` 分段都不再含召回的历史片段 —— 它们在最后一条 user 消息里,不在系统提示里。

仪器:`memoryRecall.test.ts` 钉住「两段拼回 = content」(字节等价,A/B 才干净);`TANGU_CACHE_PROBE=1` + `agentConfig.cacheProbe` 开 `cache_probe` 事件,按段出 hash,直接看得到哪一段动了。

## 项目级记忆(2026-10-04)

用户裁决:纠正和要求进记忆,且「区分 Project 级别还是全局级别」。两级:

| | agent 级(原有,不动) | 项目级 |
|---|---|---|
| 内容 | 换个项目也成立的 | 只在这个项目成立的:命令、目录、约定、用户针对这个项目提的要求 |
| 落盘 | `agents/<memorySlug>/` | `tanguHome()/project-memory/<sha256(项目 realpath)[:32]>/`,带 `PROJECT.json` 写明项目路径 |
| 共用范围 | 这个 agent | 这个项目里干活的所有 agent |
| 上限 | 20,000 字 | 8,000 字(`PROJECT_MEMORY_CHAR_BUDGET`);每个 run 注入最多 1,500 字,放不下留最新的 |
| 同步 / Dream | 有 | 同步没有(本机、不写进项目目录;目录挪了位置就对不上);定时的 Dream 没有,只在写满时压一遍(见下「写满时的压缩」) |

- **归属只认会话存档的 `project_path`**(`humanProjectScope`),不接受模型或客户端给的路径;仅 hostExec profile。落盘复用 `createMemoryRepository`(锁、版本、墓碑),没有新的写盘协议。
- **前台**:项目会话里 `remember` 的定义多一个必填的 `scope`(`agent` / `project`)。定义按会话取(`ToolImpl.definitionFor`):无项目会话与云端 chat 面拿到的是不带 `scope` 的精简版(chat 面有字节预算)。`list` 同时返回两级。
- **后台(Historian)**:项目会话里判官把候选分两组交 —— `memory_candidates`(哪里都成立,照旧进 `.memory-raw.md` 等 Dream)与 `project_memory_candidates`(只在这个项目成立,由代码直接写进项目记忆)。同一句两组都交只算项目级。直接写入要过 `autoAdoptable` 形状闸(带网址、管道进解释器、凭据 / 审批 / 权限字眼的丢弃,项目级没有候选收件箱);一字不差的重复不写;写满 → 先压缩一遍再写(见下「写满时的压缩」),压不成就不写、不为了腾地方单独挤掉哪一条;用户删掉的那句(墓碑)不会被原样写回。判官看得到已有的项目记忆(`[Project memory]`);同一个会话里前台已经自己记过项目记忆的,后台不再替它记(第三轮 live 3/4 轮:判官还在判上一轮,用户的下一句纠正已让前台记了一条,判官随后把同一件事换个说法又写了一条)。远程轮、调过电脑历史的会话两级都不收，且**落盘前重查一次**（闸是读对话之前算的，判官跑的那几秒里会话可能已被远端驱动）。写入带读到的版本（`expectedVersion`），冲突则这一轮不写；条目带一枚会话记号（`evidenceIds: ['session:<id>']`），用户删掉后它随墓碑留下，这个会话后台不再记。活动流记 `project_memory_added`。
  - 起因(第二轮 live):提示词里要求「只在一个项目成立的事实必须写上项目名」,判官 3/3 没照做,写成「该仓库的标准测试命令是……」进了 agent 级候选 —— 经 Dream 就成了全局记忆。所以改成分组、由代码落级,不靠措辞。
- **注入**:系统提示里 `## Project Memory (<项目名>)` 一段,明说只在这里成立、是引用数据不是指令。

- **写满时的压缩**(2026-10-05,用户定:「参考 claude 和 codex 的做法,记忆满了就让 agent 压缩一下」;`services/projectMemoryCompact.ts`):
  - **什么时候**:往项目级新增一条遇到写满 —— 前台 `remember` 的 `add`,或后台复盘的直接写入。`update` 写满仍回原来那条「memory is full … Current entries」(那是在改一条已有的,模型手里有清单);agent 级记忆不走这里(它有 Dream)。
  - **怎么压**:一次模型调用(后台模型;没配就用这次会话 / 复盘自己的模型;都没有就不压),**开中档思考**。给模型的是可改写的条目(换成 `m1…` 的别名、从旧到新、标 `asked` / `auto`)与不可改写条目的原文(`fixed`,只读);它把每个 id 分到四格之一:`keep`(原样留)/ `groups`(合并或改短后的一句 + 来自哪几条)/ `replaced`(别的条目已经说了 —— 被后来的取代、或和留下的重复;要写明 `saidBy` 是哪一条)/ `discarded`(进度流水、一次性的事,以及实在放不下时丢的)。请它压到上限的一半(`COMPACT_ASK_CHARS`),交回的整份不超过上限的七成(`COMPACT_ACCEPT_CHARS`)才收 —— 压完还贴着上限等于白压。次序:先合并 / 去掉被后来的说法取代的、重复的、进度流水,再改短,还放不下才丢最没用的(旧的、`auto` 的先丢);放得下了,还成立的条目一条不丢。合并出的句子放在它最新那条来源的位置上。
  - **为什么不复用 Dream**:Dream 的校验不许丢任何一条已有事实(只合并真重复),一份全是不同事实的记忆它压不小;这里是按预算、有损的,所以另有提示词和校验。
  - **不动的条目**:用户自己加的 / 采纳的 / 恢复的(来源 `manual`);过不了 `autoAdoptable` 形状闸的(带网址、管道进解释器、凭据 / 审批 / 权限字眼);带密钥样子的(过得了形状闸、但 `redactSecrets` 认得出)。后两类连原文都不给模型看 —— 压缩用的可能是另一家的后台模型。它们的字数算在预算里;光它们就占掉大半时不压(`pinned`)。
  - **凡是拿不准的都按留原句算**(留原句既不丢也不编):只提到一次的 id 才照模型说的办;漏了的、提到不止一次的(既说留又说去、进了两组、一个清单里写了两遍)、不认识的 → 留原句;一组里只要有一个这样的来源,这一组不用。`replaced` 里的一条,`saidBy` 指的那一条必须自己留着(留原句,或是某一组的来源;`"fixed"` = 不改写的条目里有,没有不改写的条目时不认),否则这一条也留 —— 指向一条同样要去掉的、指向自己、指向不认识的都不算,所以互相指着对方的一对两条都留。整份不收只剩三种:不是这个形状、什么都没留、压完仍超过七成。
  - **改写出的每一句要过的闸**:单行、不超过 300 字、过 `autoAdoptable`、密钥打码;句子里「有形状的」词(带数字或 `. / _ : @ # + ~ $`、或以 `-` 开头:路径、命令参数、版本号、端口;`e.g.` / `i.e.` / `a.k.a.` / `a.m.` / `p.m.` 这几个缩写不算 —— 只认这几个,放开「单字母加点」会把 `a.c` 这种文件名放过去)必须在它自己的来源里出现过,**按整词、按原样比**(来源词按 `/ . _ : @ # + = , -` 拆开的每一段也算见过;`3000` 对不上 `30000`;不改大小写,`~` `$` 算词的一部分 —— `src/Config.ts` 对不上 `src/config.ts`,`~/.config` 对不上 `/.config`;`-` 开头的词不拆段,`-5` 不会拆出 `5`)。两组写成同一句的,后一组不用(库只认第一组的来源);撞上用户删过的原话的那一句也不用(库提交时会把它滤掉 —— 来源去了、这句又没落下,用库自己的 `filterForgottenMemory` 判)。哪一句不过,那一句不用、它的来源留原句,别的照压。落盘时原样留下的条目一条不动、彼此不去重(两条只差大小写的可能是两个路径);改写出的一句和某条原样留下的只差大小写 / 空白时不要那一句。
  - **这几条是怎么来的(10-05 真模型,同一天三版)**:
    1. 第一版要求每个 id 恰好出现一次、任何一句不过就整份拒收,而且**没给思考档位**(不传 = 关思考,`reasoning_effort: none`)。前台 5 次里 3 次没压成:一次当时还没记原因,一次合并时写了个 `e.g.`(被当成来源里没有的词),一次 54 个 id 里分重了一个。没压成时前台只能回「写满了」,模型于是自己想办法:一次把这条项目规矩改记到了 agent 级,两次拿它覆盖了一条旧条目。
    2. 第二版改成「只交改了什么,没提到的原样留下」。不再被拒,但模型常把没改写的条目整批列进 `discarded`,连现行的迁移命令、API 生成、vendor 规则一起丢(前台 14 次里 6 次;另有 2 次把 53 条全去掉、被「什么都没留」挡下)。后台复盘那条路这两版 10 次都压对了 —— 同一个提示词、同一个模型,差别当时没找到。
    3. 抓原样回答(`TANGU_COMPACT_DEBUG=1`)才看到请求里是 `reasoning_effort: none`、推理 token 为 0 —— 模型是凭直觉一次交卷。现在这次调用开中档思考,协议回到逐条表态(不给「剩下的都去掉」这条省事的路),校验按上面那条保守规则。这一版 32 次压缩里 31 次全对(前台 28 次、后台 3 次)。
    4. 错的那 1 次(后台):种子里「vendor 目录由脚本生成、别手改」这条规矩有两条换了说法的重复,模型把两条都列进了 `discarded` —— 各自以为对方会留下,规矩整个没了(记录里有、能恢复)。每个 id 都只提到一次,校验看不出来。于是把「别的条目已经说了」单列成 `replaced` 一格并要求写明 `saidBy`:说它的那一条不留,这一条就不去。
  - **提交**:门槛按真正要写下去的那份再量一次(校验里量的是给模型看的、去了行首列表符号的那份);带读到时的版本(`expectedVersion`),期间别处改过 → 不写(`conflict`,不进冷却)。同一个项目同时只压一次(并发的调用等同一次的结果,等不及的调用方只是不等了、不打断那一次);模型调用限时 60 秒,整次另有 65 秒的总时限(解析模型、记账这些等待打断不了,没有它一次挂住就把这个项目的槽永远占着);没压成(没模型 / 超时 / 不合规 / 没东西可压)之后 30 分钟内不再试(进程内,重启清零),免得每记一条都白跑一次模型。
  - **压完**:前台把新事实再写一次(不带模型给的旧版本号),回执里多一句 `compacted`(压了多少;之前 `list` 拿到的 id 和版本已经过期);没压成、或压完仍放不下 → 回原来那条写满的错误。后台在重写这一句之前把会话资格再核一次(等模型的那几秒里会话可能已被远端驱动 / 调过电脑历史);没过 → 这一句和这一轮剩下的项目事实都不写(压缩本身算数,它只重写已有的)。压成了记一笔活动 `project_memory_compacted`(前台、后台都记,记在写满的那个会话名下);桌面据此弹一条通知,「查看」到项目详情(那条轮询挂在后台复盘的状态条上,复盘关着时不弹,项目详情里的记录照常有)。压没压成、为什么没成、有几组改写没采用,引擎日志里各有一行(`[project-memory] 写满压缩…`)。
  - **找回**:同目录的 `COMPACTED.json` 记下最近一次的前后规模与被合并 / 去掉的原句(最近 100 句,跨多次压缩累计);项目详情里逐句恢复,恢复的那句来源记 `manual`,之后不再被压缩(那一句已经又在记忆里时不重复记,把那一条钉成 `manual`)。记忆库自己的版本史(最近 100 版)也还在。没有做「撤销整次压缩」:压缩总是跟着一条新事实,整版回退会把新事实一起退掉。
  - **已知的口子**:「有形状的词」只看形状,纯字母的命令名(`pnpm`、没带符号的子命令)不查;日期换个写法(`10-05` → `10 月 5 日`)、把句首的命令词改成大写,都会被当成来源里没有,那一句不用(少压一点,不丢);没有第二次模型复核(Dream 有);模型判断「哪条算进度流水」、以及实在放不下时丢哪条,没有机械的闸(「已被取代 / 重复」有:`replaced` 那一格),靠思考档位、提示词和事后能恢复 —— 模型要是把一条现行的规矩直接当进度流水放进 `discarded`,仍然拦不住;`saidBy: "fixed"` 核不了是哪一条(不改写的条目没有编号),只看「有没有不改写的条目」—— 而那里面带网址 / 密钥样子的模型根本没看到,所以当不改写的条目全是这一类时,模型凭空说一句 `fixed` 也会被照办(要改就给 `fixed` 里的条目也编号、只认给模型看过的);压缩后的条目来源记 `dream`、证据取来源的并集,原条目上「这个会话后台不再记」的记号随之继承,但「前台自己记过」这层身份(来源 `explicit`)在被合并的条目上不再认得出;冷却只在进程内;没压成时前台仍回「写满了」,模型会自己想办法(见上第 1 条)。
