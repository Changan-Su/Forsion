# Agent 隔离记忆与 Dream 整理

2026-09-08 实现。参考 Hermes 的小常驻记忆与按需历史检索、Hanako 的来源覆盖与提交前验证、OpenClaw 的遗忘标记；按 Tangu 现有多 Agent 架构重新接入，没有引入它们的全局记忆池。

## 使用

- 对话里的 `remember` 支持 `add`（默认）、`list`、`update`、`forget`。更新/遗忘先取得条目 ID；工具回执只含实际持久化后的版本与**受影响的那一条**（不再整份 entries 回灌上下文；重复写入回 `duplicate: true`）。Chat 模式也可用。失败不能宣称“已记住”。
- **形状闸（2026-09-22，借 Hermes memory 工具）**：单条 `fact` 超过 300 字直接拒绝并指向 `log_event`（与 Historian 候选采集的 300 字截断同口径）；描述与运行时指引明说「记忆 = 下个月仍成立的事；进度 / 交付物 / 版本号 / 带日期的进度汇报归日志」（生日、财年截止这类带日期的稳定事实照记），新事实取代旧条目时 `list` → `update` 原地替换而不是再加一条「更正」；记忆满（20,000 字）时回执列出现有条目与版本，让模型一次删旧加新。**为什么**：一份终端用户导出里 41 条显式条目最长 1,477 字、21 条带日期、9 条是追加式更正——显式路径此前没有任何闸，而候选路径 12 天只出 8 条一句话；措辞已经写在该 Agent 的 developer_instructions 里却挡不住，只有执行层挡得住。辅助模式讨论同步注入整份记忆（受同一 20k 帽）而非头 3,000 字，否则主 Agent 看不到最新条目。
- 设置 → 智能体 → 某个 Agent 的记忆：查看/编辑/遗忘条目、检查来源、编辑原文、查看版本与恢复。原文和日志编辑必须提交读取时的版本；409 保留草稿，先刷新后合并。
- Dream 在同一面板中操作。可单次“立即整理”，也可单独关闭此 Agent 的自动整理，设置模型、最小间隔、总时限与输出预算。模型留空沿用已配置的后台模型（与 Historian 同一条解析链）。
- **自动整理自 2026-09-19 起默认开启**（此前默认关闭）。原因：Historian 只写候选，Dream 是候选进入 MEMORY.md 的唯一通道；默认关闭时，原装安装会一直采集候选却永远记不住。配套三条：①`.memory-dream.json` 带版本标记 `v: 2`——没有标记的旧文件里的 `enabled: false` 是旧默认值随状态写入顺带落盘的，不是用户的选择，读作开启；带标记后的 `false` 才是用户关掉的，永久保留。②自动运行在“没有已核验的新候选、且记忆版本就是上次整理产出的那一版”时直接跳过，不调用模型；手动整理不受此限。③没有可用后台模型时自动运行记为跳过而非失败。
- 辅助模式（`historian.mode = 'assist'`）的到点轮同样检查整固：辅助模式只表示本轮不由 Historian 采集候选，收件箱里已有的候选仍只有 Dream 一条路进入记忆。
- Historian 仍单独控制从对话采集候选。关闭 Historian 时，Dream 可以整理已显式保存的记忆，不会擅自扫描所有对话来创建候选。

## 隔离契约

记忆条目、版本、墓碑、候选和 Dream 状态属于 `agents/<memorySlug>/`。模型工具没有可自行指定的 `agentSlug` 参数；其身份来自可信运行上下文。历史搜索与读取另外按 `(userId, appId, activeAgentSlug)` 检查归属，猜中另一个 Agent 的 session/message ID 也不能读取。无 Agent 标记的旧会话只归默认 Agent。

保留用户已有的 `shareDefaultMemory=true` 例外：该 Agent 明确共用默认记忆域；展示身份、会话归属仍是原 Agent。后台同步使用展示身份选文件，不能把 memorySlug 当成同步目标。新开云同步默认不授权旧全局 USER/MEMORY 池；共享必须另有显式配置。管理者界面仍可以查看自己的各 Agent。

这是应用层作用域，不是多个 OS 用户。Tangu 本地数据库和 home 仍是每安装单用户。是否约束任意主机命令，取决于另行配置的 OS 沙箱；参见 [runtime-safety.md](runtime-safety.md)。记忆/日志/历史工具是固定参数的可信应用状态入口，不接受任意磁盘路径。计划模式原有写入限制继续适用。

## 存储、遗忘与恢复

- `.memory-state.json` 是事务真源：活跃条目、UUID 版本、来源/证据 ID、最多 100 条历史修订、遗忘/重新记住事件、最近 8192 个已处理候选 ID。`MEMORY.md` 是兼容人工编辑的投影。
- 同目录短事务互斥；临时文件、fsync、原子 rename；`projectionPending` 能恢复“元数据提交后、Markdown 投影尚未完成”的中断。网络和模型调用不持有目录锁。
- 文件不存在与 EIO/EACCES、损坏 JSON、未知结构明确区分。损坏/读失败不会伪装为空白覆盖旧数据。已有 state 时直接删掉 MEMORY.md 是损坏，不是遗忘。
- `forget` 删除活跃记忆并留下防重放事件；自动检索排除已知遗忘原文/证据，Dream 与同步不能用已知旧来源恢复它。版本恢复也不自动复活遗忘条目。只有显式 add/update 可以有意重新记住。
- 跨设备合并分别保留最新的 forget 与 restore 时间；观察到遗忘后的显式重新记住优先，无法判定先后的同时间冲突以遗忘优先。
- **遗忘不是物理擦除**：版本历史和墓碑仍含原文供审计；对话原文也不会因此被删除。对未知来源的语义改写，不能保证靠指纹自动识别。不要将此功能描述成账户数据彻底删除。

若进程在持锁时崩溃，遗留 `.memory.lock` 会明确返回 `MEMORY_BUSY`，不会按年龄抢走可能仍在使用的锁。恢复步骤：停止此 home 的全部 Tangu 引擎/Desktop/TUI，核对锁内 PID 已退出，备份该目录的锁、state 与 MEMORY.md，将锁移到备份位置后重启。读取会按 pending 标记恢复投影。不要在其他写者仍运行时盲删锁；无法确认归属时保留现场。

## Dream 提交流程与预算

1. 读取此 Agent 的版本快照，并根据事务中的候选回执补做上次未完成的收件箱清理。
2. 轮转读取最多 12 个候选（无证据旧条目不会阻挡后续候选），校验来源会话归属，按采集时的消息锚点读取有界证据。不能核验的候选留待审阅，不交给模型自行丢弃。
3. 一次模型调用提出按 source ID 分组的事实与候选丢弃理由。代码要求所有既有事实被覆盖恰好一次，未知 ID、重复覆盖、遗漏、删除已有事实、超过 20,000 字符或截断输出均拒绝。**`keep`（2026-09-22）**：未变的既有事实只回 ID，校验器按存储顺序展开成原文后再提交——输出随改动量而不是记忆总量增长（此前要逐字重发全部事实，17k 字的记忆估 ~7.7k tokens，默认 3,072 输出预算永远塞不下）。给模型看的 source ID 是短别名 `m1…`/`c1…`（UUID 一个 ~25 token，几百个 keep 本身就能撑爆输出预算），提交前映射回真 ID；核验调用拿的是紧凑形（keep 的 ID + 改动组），不把 keep 展开成原文再灌一遍。
   - **输入预算按余量裁证据（同日）**：32,000 字符预算 = 既有记忆 JSON + 候选证据；候选逐条按余量裁证据尾窗（锚点消息在末尾，留尾），低于 1,000 字符的**跳过继续**（后面窗口更短的候选照样能塞下），跳过的和来源查询抛错的都留在收件箱、游标照常越过（转到队尾，不会每轮堵在最前让 Dream 永远失败），状态里写明 `N deferred by the input budget`。此前 12 条 × 8k 证据不看余量，记忆稍大整轮即 `failed, calls: 0`，每 6 小时原样重演、收件箱永不排空。既有记忆单独超预算仍是明确失败（只可能来自面板 / 同步写入的超帽内容）。
4. 第二次调用核验事实、条件、路径、日期及例外没有丢失，候选有对话证据支持。不会为了通过验证反复追加修复调用。
5. 用读取时的版本 CAS 提交正文、来源和候选处理回执。并发修改则拒绝，原记忆和候选保留。提交后清理失败可下次恢复；已经提交就报告已完成，不能误报成取消。

默认每 Agent 间隔 6 小时、总时限 60 秒、两次调用合计最多 4096 输出 tokens（提议 75%，验证 25%），进程同时最多 2 个 Dream；不排无限队列。自动触发依附用户 run 完成，不是独立定时守护。Historian 自己最多 2 个同时运行、单次总时限 90 秒。

Provider 的 build/stream 接收真实 AbortSignal；每次持久化前再次检查取消。若第三方适配器忽略信号，状态会说明正在等待停止，保持单飞且拒绝迟到结果；不能把超时当成实际请求已经结束。模型和同步已经在远端提交的副作用不能靠客户端取消撤回。

## 前台性能与历史召回

每个 run 冻结最多 **4000 字符**记忆上下文：约 1000 常驻、2000 相关条目、1000 相关历史证据，包含来源标签的总量也受硬帽限制。采用本地词法相关性，支持中文分词；没有嵌入请求，也没有全库建索引阻塞启动。

自动历史窗口最多 16 会话 × 每会话最近 16 条 × 每条前 2000 字符；显式 `search_sessions` 最多 64 × 64 × 4000。搜索结果提供原始 message ID，`read_session` 支持精确回读/翻页；找不到时应提示窗口限制并用日期缩小范围，不能声称已穷尽全部历史。没有持久派生索引，所以会话 purge 后不会从旧索引复活。

Agent 定义已有有效本地快照时立即开跑，云文件同步在后台进行；只有首次水合等待云端，带 15 秒总 deadline/取消。缺失或失败不会偷偷换成默认 Agent 继续。同步逐请求、逐本地提交复核账号来源、授权修订和取消状态；LOG 在网络返回后重读并 CAS，部分失败明确返回失败。

云端只接受固定文件名单、合法 slug、真实日期和无穿越的路径，拒绝逐段 symlink；记忆 tombstone wire 为 `.memory-tombstones.json`，配置、候选、事务 state 与本机运行状态不镜像。旧云端不支持必要的 seq/hash/CAS 时，危险覆盖会明确拒绝，需升级服务端，不能退回悄悄覆盖的 LWW。

## 本地合成性能记录

2026-09-08，Node 22.23.1 / Apple M5 / 内存 SQLite：2 个 Agent，各 10 个会话、1000 条消息与 20,000 字符记忆。预热 3 次后测 20 次，召回 p50 **9.88 ms**、p95 **13.83 ms**；每次 11 条 SQL，注入 **2841 字符**，无跨 Agent 内容。此记录不含网络、模型推理或生产尾延迟，不能据此承诺对话整体提速倍数。原始样本见 [memory-recall-benchmark.json](memory-recall-benchmark.json)。

## 召回块的落点(2026-09-14 起)

`buildAgentMemoryContext` 返回的三段现在分开出账:`stable` = §1 存储证据(与本条消息、本会话都无关,Dream 之间稳定),`volatile` = §2 按查询打分 + §3 跨会话历史片段(带 `[session_id=…; message_id=…]`,每条消息都不同)。`content` 仍是整块,恒等于 `[stable, volatile].filter(Boolean).join('\n')`。

落点由 `TANGU_MEMORY_VOLATILE` 决定:

| 取值 | 易变段去哪 | 用途 |
|---|---|---|
| `tail`(缺省) | 对话尾部 user 消息(与 `/skill`、`@` 提及、运行时 git/todo 同一条通道),不落库不上屏 | 让系统提示前缀跨会话可共享 |
| `system-end` | 仍在系统消息里,但挪到 `systemParts` 最末尾 | 变体 S:不改「记忆是 system 角色」的权重 |
| `system` | 旧位置(记忆块整块留在系统提示 44% 处) | A/B 基线,与改动前逐字节一致 |

稳定段恒留原位。`sketchTurnSignal`(按本条消息的正则取 3 种值)跟易变段同一落点。

**为什么**:易变段卡在系统提示中部,等于每来一条新消息就把它后面的技能目录与 ~13k 工具头一起从缓存里作废;实测同 agent+模型的不同会话,系统提示正是在记忆块处首次分叉。

**代价**:`tail` 档下,开发者「显示 system prompt」事件与 context 视图的 `memory` 分段都不再含召回的历史片段 —— 它们在最后一条 user 消息里,不在系统提示里。

仪器:`memoryRecall.test.ts` 钉住「两段拼回 = content」(字节等价,A/B 才干净);`TANGU_CACHE_PROBE=1` + `agentConfig.cacheProbe` 开 `cache_probe` 事件,按段出 hash,直接看得到哪一段动了。
